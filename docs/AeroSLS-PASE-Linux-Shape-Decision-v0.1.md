## Context

The project has used “PASE” in two different senses. IBM PASE is an AIX binary-compatibility runtime inside IBM i. The v0.1 POSIX-Environments roadmap explicitly mapped the *shape* of PASE onto an on-demand POSIX environment inside a partition, but the binary-compatibility half arrived later as a **static x86-64 Linux ABI shim** (E7), not AIX compatibility.

That ambiguity is now a product decision, not an implementation detail. Continuing to call the Linux ABI shim “PASE” without qualification would invite expectations it cannot meet: AIX binaries, Power, shared libraries, AIX libc and IBM i user profiles are all different targets.

## Decision

AeroSLS adopts the **PASE-shaped Linux runtime** target.

- The compatibility target is **x86-64 Linux**, not AIX/Power.
- The shipped image contract is static, non-PIE `ET_EXEC` first; dynamic linking is a planned later increment (M2), not part of the current contract.
- The isolation model stays the POSIX environment inside a partition, with the Linux task holding exactly one capability: the channel to its environment's sidecar.
- Native data access is a mediated, partition-scoped surface. The read-only catalog and `CAT_QUERY` are the first cut; a write path, IFS-like sharing, identity/ACL and native-SIMI reach are later increments (M5).
- The cluster/durability work (P1a–P3) remains part of the environment story; it is not an AIX compatibility feature.
- The public and technical description should say **“PASE-shaped Linux runtime”** or **“PASE equivalent”**, never unqualified “IBM PASE.”

This is a Linux-shape decision. It does not claim that AIX binaries run, that Power is supported, or that the project is a drop-in IBM PASE replacement.

## Explicit non-goals

- AIX binary compatibility, AIX libc, Power, or IBM i job/user-profile semantics.
- Nested environments; the v0.1/v0.2 closure stands.
- Hardware capabilities for tenant environments; the zero-hardware-cap tenant profile stands.
- Zero-downtime live migration; P3 pauses the environment for transfer.
- A general POSIX-complete runtime in one step. The measured syscall surface and named milestones define the increments.

### M5.1/M5.2 status (2026-11-17)

M5.1 is landed and evidenced. M5.2's syscall path and gate-profile harness are present in the tree; its live evidence is not yet committed, and the tenant arm remains M5.2a.

The M5 exit gate above is the milestone-level requirement. It is split into two increments so the first cut does not claim a Linux-task path it does not have:

- **M5.1 — POSIX-mediated write (first cut).** **Status: LANDED 2026-11-17; evidence in `evidence/m5_1_20261117/`.** The write surface is `CAT_EXEC` (verb 6: one DML statement in an explicit begin/execute/commit transaction, no DDL or multi-statement transaction), reached by a **POSIX-sidecar task** — the environment's `sh` running the `catalog exec` applet — through the existing `catalog` cap and `CatalogOps`/`CatalogClient` chain. The kernel binds identity from the registered channel (`owner_uid`), requires a nonzero live owner in the channel's partition, applies `catalog_check_access(..., PERM_WRITE)`, and replies `CAT_OK` only after `sql_tx_commit` succeeds; a failed execute rolls back, and a failed commit never becomes `CAT_OK`. A native SLS observer must see the committed change; a foreign-partition name answers `CAT_ERR_NOENT`, and a denied write leaves the row unchanged. This cut proves mediated native↔POSIX write and native visibility, but it does **not** satisfy the “Linux task writes” clause.
- **M5.2 — Linux-task syscall follow-up.** **Status: syscall and gate-profile harness are in the tree; no committed live evidence yet.** A Linux-personality task reaches the same `CAT_EXEC` service through the project-private Linux syscall `SYS_SLS_CATALOG_EXEC` (334). The kernel copies the bounded SQL request into the existing forwarded syscall message; the sidecar's `linux::service` calls the same `CatalogOps::cat_exec` method, not a second catalog client. The task still holds exactly one capability — its channel to the environment sidecar — and identity remains the environment's channel-bound owner; the syscall carries no uid. This increment also needs a tenant Linux-task spawn/test surface, because ordinary tenant environments do not spawn a Linux personality today.

#### M5.2 syscall test boundary

The syscall test has a narrow surface and a narrow claim.

- **Surface.** Only a Linux-personality task may issue `SYS_SLS_CATALOG_EXEC` (334); it reaches the same `CAT_EXEC` service through its one sidecar channel. The request carries a bounded SQL pointer/length and flags, never a uid, table partition, capability or second statement. `linux::service` must call the existing `CatalogOps::cat_exec`; a test that lets the syscall reach `kernel.env.catalog` directly is testing the wrong architecture. The first cut still refuses DDL, joins, subqueries, multi-statement text, foreign partitions and FK-connected tables exactly as M5.1 does.
- **ABI and negative cases.** Host-test the kernel copy-in before any catalog call: null/bad pointer, zero length, over-`CAT_SQL_MAX`, NUL, wrong personality, and a request that would carry a second statement must fail without opening a transaction. Test the sidecar arm with a fake `CatalogOps` to prove it reuses the one client, maps `CAT_ERR_*` to Linux errno, and does not add a second catalog cap to the task. The existing E7 cap-table guard remains the check that the Linux task still holds exactly its sidecar channel.
- **First live harness.** The `e7_gate` profile already carries the `catalog` cap and spawns a Linux first-user task. `user/sidecar/fixtures/e7_catalog_probe.S` invokes `SYS_SLS_CATALOG_EXEC` against a bob-owned table, and `tests/m5_catalog_live_check.sh` drives the gate-profile arm: the write succeeds, a native observer sees it, a write to dave's table is denied with the row unchanged, and a foreign name is `NOENT`. This proves syscall dispatch, copy-in, sidecar reuse, identity/ACL and native visibility. The arm has not yet produced a committed evidence record.
- **Claim boundary.** The gate-profile arm is a syscall-path proof, not a normal-tenant proof: ordinary tenant environments do not spawn a Linux personality today. M5.2 is not complete for tenant service until the tenant Linux-task spawn surface is added and the same arm runs there; if that is kept separate, name it **M5.2a** and do not count the gate-profile result as M5.2a evidence. M5.2 also does not claim IFS-like files, native SIMI reach, per-task credentials, row-level ACLs, DDL or multi-statement transactions.

M5 is complete only when M5.1 and M5.2 are both evidenced, and the M5.2 claim names whether its evidence is gate-profile-only or includes the M5.2a tenant arm. M5.1 now meets its half; M5.2 remains incomplete until its live evidence is committed and the M5.2a tenant surface is exercised if a tenant claim is made.
